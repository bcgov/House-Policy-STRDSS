# Database changes (database/)

These rules apply to new work from the sprint after August 2026 onward. Scripts from Sprint 22, August 2026 and earlier have already run in production. Leave them as they are and do not rename or reorganise them to fit these rules.

## 1. Find the sprint name
Use the Jira sprint name on the ticket (e.g. "August 2026"), with spaces turned into underscores: `August_2026`. If the ticket has no sprint, ask the user. Sprint numbers are no longer used; existing `Sprint_N` files stay as they are.

## 2. Choose where the script goes

| Change | Location and name |
|---|---|
| Schema change | `ddl/STR_DSS_Incremental_DB_DDL_Sprint_<SprintName>.sql` (split large work with a suffix, e.g. `..._Sprint_<SprintName>_<Topic>.sql`) |
| Full schema | `ddl/STR_DSS_Physical_DB_DDL_Sprint_<SprintName>.sql` |
| Views / routines / functions | `ddl/STR_DSS_Views_Sprint_<SprintName>.sql`, `STR_DSS_Routines_...`, `STR_DSS_Functions_...` |
| Seed data in a release | `seeding/STR_DSS_Data_Seeding_Sprint_<SprintName>.sql` |
| LG seed data | `seeding/STR_DSS_Data_Seeding_LGs_Sprint_<SprintName>.sql` |
| Platform seed data | `seeding/STR_DSS_Data_Seeding_Platforms_Sprint_<SprintName>.sql` |
| Master migration script | `migrations/STR_DSS_Migration_Sprint_<SprintName>.sql` |
| One-off fixes, report queries, anything not part of a release | `utility/DSS-<key>_<Purpose>.sql` or `utility/<Purpose>_Sprint_<SprintName>.sql` |

`utility/` is only for one-off scripts and queries. Migration scripts and `STR_DSS_Master.bat` live in `migrations/`.

Example: `seeding/STR_DSS_Data_Seeding_LGs_Sprint_August_2026.sql`.

Never edit a script from an earlier sprint. Add a new sprint file instead. The exception is a script that has not shipped yet.

## 3. A schema change touches all of these in the same sprint
Never deliver only the incremental file.

- [ ] Incremental DDL: the change itself
- [ ] `Physical_DB_DDL_Sprint_<SprintName>.sql`: the full schema, so a fresh build matches an upgraded database. Start from the previous full file if no new one exists yet.
- [ ] Views, routines or functions files, if any of them changed
- [ ] `migrations/STR_DSS_Migration_Sprint_<SprintName>.sql`: state check, plus `\ir` calls for the upgrade and fresh-build branches
- [ ] `migrations/STR_DSS_Master.bat`: point it at the current migration script
- [ ] `server/README.md`: the "repository schema migration" command uses the latest migration script
- [ ] `database/README.md`: the release script list, and a change summary under "Database Change Summaries"
- [ ] `model/`: update the `.dbs` XML (DbSchema project) for the new or changed tables and columns

The `.md`, `.pdf`, `.svg` and `.png` files in `model/` are generated by DbSchema (a GUI tool). They can't be regenerated from here. In the final summary, tell the user to open the `.dbs` in DbSchema and regenerate the documentation and diagram exports.

## 4. Seeding script rules
- Safe to re-run: use `MERGE` or guarded `UPDATE`/`INSERT ... WHERE NOT EXISTS`. Never use a plain `INSERT`.
- Header comment: `/* STR DSS Sprint <SprintName> <Purpose> - <JIRA-KEY> <Ticket summary> */`.
- A seeding script that ships in a release must be called from the migration script and listed in the README.
- `organization_cd` is an immutable key and is referenced by ID elsewhere. Change it only with a seeding script that updates the existing row, so `organization_id` stays the same.

## 5. Migration (master) script
Copy the structure of the latest `migrations/STR_DSS_Migration_*.sql`. Keep:
- `\ir` with relative paths such as `'../ddl/...'`
- Everything in one transaction, with rollback on `:ERROR`
- State checks (`information_schema`) so a completed migration exits without changes
- Both the upgrade branch and the empty-database branch

Run it as the application user `strdss<env>`, never `postgres`. Only database creation needs `postgres`.

## 6. Out of scope
Leave `booking/`, `str-registry/`, `UBC/` and `UEL/` alone. They hold special-case data and shape-file working files. Their rules don't apply to sprint naming or the migration script.

## 7. Validation
No SQL test scripts are kept in this repo. Validation happens afterwards through the API and the frontend. Do not add test scripts.

## Final summary checklist (report to the user)
- Which files were created or changed
- Which companion files were updated, and which were not needed
- The DbSchema exports they must regenerate by hand
- Any assumption about codes, names or sprint
